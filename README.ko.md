# receipts

에이전트가 쓴 숫자마다 영수증을 붙이고, 영수증이 없는 숫자는 표시한다.

> **상태: 0.2.1입니다.** 대조 스크립트, 에이전트 스킬, 미국 공시(SEC EDGAR)와 한국 공시(DART) 연결이 들어 있고, 규칙을 먼저 적어 두고 돌린 평가 다섯 가지의 결과와 한계를 [아래](#평가-결과)에 적었습니다. E1, E2, E3는 0.1.0에서, E4와 E5는 0.2.0에서 잰 것이고, 0.2.1은 스캔이 `7~9월` 같은 한국어 월 범위를 읽는 방식만 바꿨습니다. 그 사이 바뀐 내용은 [CHANGELOG.md](CHANGELOG.md)에 있습니다.

[English](README.md)

## 문제

에이전트가 보고서를 쓰고 숫자를 확인했다고 말합니다. 실제로는 확인하지 않았거나 일부만 확인한 경우가 많고, 읽는 사람은 어느 숫자가 확인된 것인지 알 수 없습니다.

## 방식

모델은 계획만 쓰고, 판정은 코드가 합니다.

1. 코드가 문서의 숫자를 전부 찾습니다. 이 개수가 분모입니다.
2. 모델이 숫자마다 문장, 출처 칸, 계산식을 적습니다. 값은 적지 않습니다.
3. 코드가 출처를 읽고 다시 계산해 `verified`(확인됨), `wrong`(틀림), `unverifiable`(확인 불가)로 판정합니다.
4. 계획에서 빠진 숫자는 `uncovered`(미대조)로 나옵니다.

## Claude Code에 스킬 설치하기

```
/plugin install receipts --marketplace sinkytiger/receipts
```

한 줄 설치는 Claude Code 2.1.275 이상에서 됩니다. 그보다 낮은 버전에서는 두 단계로 합니다.

```
/plugin marketplace add sinkytiger/receipts
/plugin install receipts@receipts
```

설치한 뒤 "receipts로 report.md의 숫자를 sales.csv와 대조해 줘"처럼 요청합니다. 스킬 이름을 말하지 않았을 때 얼마나 잘 불러오는지는 아직 재지 않았습니다. 스킬은 세션마다 약 180토큰을, 실행할 때 약 4,400토큰을 씁니다(0.2.0 기준, `claude plugin details`의 추정치).

두 방식 모두 윈도우의 Claude Code 2.1.326에서 명령줄(`claude plugin install ...`)로, 설정이 없는 상태에서 설치해 확인했습니다. 0.2.0은 한 줄 방식을 Claude Code 2.1.330에서 다시 확인했습니다.

## 에이전트 없이 스크립트만 써 보기

파이썬만 있으면 됩니다. 파이썬 3.9 이상을 기준으로 썼고, 지금까지는 3.12에서만 돌려 봤습니다.

```sh
python skills/receipts/scripts/receipts.py check examples/quickstart/claims.json
```

예제 보고서는 동부 매출이 12.4% 늘었다고 쓰지만, 출처로 다시 계산하면 11.9%입니다. 결과 첫 줄은 이렇게 나옵니다.

```
9 numbers / 6 verified / 1 wrong / 1 unverifiable / 1 uncovered   (skipped: 1 date, 2 heading_number, 1 label, 3 year)
```

지금 읽을 수 있는 출처는 CSV, TSV, JSON, 마크다운 표, 일반 텍스트, 엑셀 값, 미국 상장사가 SEC에 낸 공시 수치, 그리고 한국 회사가 DART에 낸 정기보고서의 재무제표입니다.

## 미국 공시(SEC EDGAR)와 대조하기

회사가 10-K, 10-Q에 보고한 수치를 출처로 쓸 수 있습니다. 스크립트가 SEC의 EDGAR API에서 읽습니다.

```json
{"edgar": "AAPL", "concept": "us-gaap:Assets", "unit": "USD", "period": "2026-09-26"}
```

- SEC는 자동 접속 프로그램에 이름과 이메일을 밝히라고 요구합니다. 환경 변수 `RECEIPTS_SEC_USER_AGENT`에 본인 이름과 이메일을 넣어야 합니다. 기본값은 없고, 비어 있으면 요청을 보내지 않고 멈춥니다. 이 문자열은 SEC로 보내는 요청에만 들어가고 어디에도 저장하지 않습니다.
- 회사마다 한 번만 내려받아 `.receipts/edgar/`에 저장합니다. 영수증에 내려받은 날짜가 나옵니다. 요청은 1초에 5번 이하로 보냅니다(SEC 허용치는 10번).
- 기간은 날짜가 정확히 맞아야 합니다. 분기 수치와 누적 수치는 끝나는 날이 같고 시작일만 다르므로 서로 바뀌어 통과하지 않습니다.
- 같은 기간의 값이 공시마다 다르면(정정·재분류) 판정을 미루고 값들을 보여 줍니다. 계획에서 공시를 지정하거나 최초·최신 보고를 고르면 그 값으로 대조합니다.
- `receipts.py edgar concepts AAPL --match revenue`, `receipts.py edgar facts AAPL us-gaap:Assets`로 회사가 쓰는 항목 이름과 기간 날짜를 찾습니다.
- 부문별·제품별·지역별 수치는 이 API에 없습니다. 회사가 직접 정의한 항목도, 살펴본 5개 회사에서는 들어 있지 않았습니다.
- 배당 지급일처럼 기간이 하루인 수치는 SEC가 날짜 하나로 저장합니다. 날짜 하나로 지정해도 되고 하루짜리 범위로 지정해도 됩니다.

[examples/edgar](examples/edgar)는 애플의 2026 회계연도를 다룬 짧은 글이고, 숫자 하나를 일부러 틀리게 썼습니다. SEC가 2026-11-20에 돌려준 자료를 잘라 낸 사본이 들어 있어 네트워크 없이 돌아갑니다.

```sh
python skills/receipts/scripts/receipts.py check examples/edgar/claims.json --edgar-cache examples/edgar/snapshot
```

```
7 numbers / 6 verified / 1 wrong / 0 unverifiable / 0 uncovered   (skipped: 1 date, 1 identifier, 3 year)
```

글은 연구개발비가 매출의 10.6%라고 쓰지만, 공시된 두 수치로 다시 계산하면 9.6%입니다.

## 한국 공시(DART)와 대조하기

DART에 낸 정기보고서(사업보고서, 반기보고서, 분기보고서)의 재무제표 금액도 출처로 쓸 수 있습니다. 스크립트가 금융감독원의 OpenDART API에서 읽습니다.

```json
{"dart": "005930", "year": 2026, "report": "q3", "fs": "CFS", "statement": "IS",
 "account": "dart_OperatingIncomeLoss", "column": "thstrm_amount"}
```

- DART는 이용자마다 무료 인증키를 줍니다([opendart.fss.or.kr](https://opendart.fss.or.kr)). 약관은 키를 남이 쓰게 하는 것을 금지합니다. 본인 키를 환경 변수 `RECEIPTS_DART_KEY`에 넣어야 합니다. 기본값은 없고, 비어 있으면 요청을 보내지 않고 멈춥니다. 키는 DART로 보내는 요청에만 들어갑니다(시험용 변수 `RECEIPTS_DART_URL`을 직접 설정하면 그 주소로 갑니다). 저장 파일, 영수증, 어떤 메시지에도 남기지 않습니다.
- 보고서마다 한 번만 내려받아 `.receipts/dart/`에 저장합니다. 영수증에 내려받은 날짜와 공시 접수번호가 나옵니다. 요청은 1초에 5번 이하로 보냅니다.
- 사람들이 자주 섞는 것을 위치에 모두 적게 합니다. 연결인지 별도인지(`fs`, 기본값 없음), 어느 재무제표인지, 어느 열인지입니다. 반기·분기보고서에서 3개월 수치와 누적 수치는 같은 줄의 서로 다른 열입니다. 문장이 어느 쪽을 말하는지 계획에 적어야 하고, 영수증에는 그 열이 어떤 기간인지 찍힙니다.
- DART API에는 보고서의 최신본만 있습니다. 계획에 문서가 쓴 공시의 접수번호를 적어 둘 수 있습니다. 그 뒤 보고서가 정정됐으면 다른 수치와 견주지 않고 판정을 미룹니다.
- `receipts.py dart company 삼성전자`, `receipts.py dart accounts 005930 --year 2026 --report q3 --fs CFS`로 회사 코드와 보고서의 줄, 그리고 각 열이 어떤 기간인지 찾습니다. 금액은 보여 주지 않습니다. 계획은 값이 맞는지를 보고 쓰는 것이 아니라 그 줄이 무엇을 뜻하는지를 보고 써야 하기 때문입니다.
- 금액은 보고서가 쓰는 통화의 기본 단위입니다. 거의 모든 회사가 원 단위이고, 문서에는 `107조 4,405억원`처럼 써도 됩니다.
- 자본변동표, 주석, 부문별 수치, 잠정실적, 2015년보다 앞선 사업연도는 다루지 않습니다.

규칙은 [plan-format.md](skills/receipts/references/plan-format.md) 2절과 9절에 있습니다.

[examples/dart](examples/dart)는 삼성전자의 2026년 3분기를 다룬 짧은 글이고, 숫자 하나를 일부러 틀리게 썼습니다. DART가 2026-11-21에 돌려준 자료를 잘라 낸 사본이 들어 있어 네트워크도 키도 없이 돌아갑니다.

```sh
python skills/receipts/scripts/receipts.py check examples/dart/claims.json --dart-cache examples/dart/snapshot
```

```
7 numbers / 6 verified / 1 wrong / 0 unverifiable / 0 uncovered   (skipped: 7 date, 1 year)
```

글은 3분기 순이익을 194.0조원이라고 쓰지만, 이는 1~9월 누적 수치입니다. 3분기 석 달만 보면 75.1조원입니다.

## 평가 결과

평가마다 규칙을 [docs/eval-plan.md](docs/eval-plan.md)에 먼저 적고 나서 돌렸습니다. 릴리스마다 최종용 문제를 쓰기 전에 코드를 한 커밋에서 동결했습니다. E1, E2, E3(0.1.0)는 `a84647c`, E4(0.2.0)는 `2ae4742`입니다. E1, E2, E3의 최종용 문제는 각각 한 번 돌렸습니다. E4는 앞의 두 번이 중간에 끊겨 채점을 세 번 했고, 경위는 E4 절에 적었습니다.

| | 묻는 것 | 최종용 결과 |
|---|---|---|
| **E1** | 계획이 맞을 때 스크립트가 맞게 판정하는가? 합성 문서 64개, 문장 960개, 그중 288개에 오류를 심음. | 통과 기준 8개를 모두 충족했습니다. 심어 둔 오류를 통과시킨 경우도, 맞는 문장을 틀렸다고 한 경우도 없었습니다. |

### E1: 스크립트만

모델은 쓰지 않습니다. 생성기가 문서, 출처, 정답 계획을 만들고 문장의 30%에 오류를 심습니다. 최종용 문제에서 나온 결과입니다.

- 심어 둔 오류 288개가 모두 틀림으로, 맞는 문장 672개가 모두 확인됨으로 판정됐습니다.
- 칸을 하나도 못 찾거나 여러 개 찾는 위치 지정 48건은 모두 확인 불가로 나왔고, 없거나 깨진 출처 48건에서는 모두 멈췄습니다.
- `scan`은 문장 속 숫자 960개를 모두 찾았고, 계획에서 뺀 숫자 128개는 모두 미대조로 표시됐습니다.

이 결과는 계획이 맞을 때 스크립트가 맞게 읽고 비교한다는 것을 보여 줍니다. 문서는 문장 틀로 만든 합성 문서이고 영어와 한국어가 절반씩이라, 실제 보고서는 이보다 지저분합니다.

### E2: 모델이 계획을 쓸 때

같은 문서 30개를 같은 모델, 같은 요청 설정으로 두 방식으로 돌렸습니다. A 방식은 모델이 스킬 설명서와 스크립트가 뽑은 문서 속 숫자 목록을 받고 계획을 쓰면 스크립트가 판정합니다. 계획은 두 번까지 고칠 수 있습니다. B 방식은 모델이 문서와 출처를 한 번에 받아 직접 검토하고 틀린 숫자를 적습니다. 스크립트의 출력은 받지 않습니다. E2에는 통과 기준이 없습니다.

| | A: 스킬과 스크립트 | B: 모델 혼자 |
|---|---|---|
| 심어 둔 오류를 잡음 | 128개 중 128개 (95% 구간 97.1%~100%) | 문장이 있는 줄을 지적하면 인정할 때 128개 중 125개 (93.3%~99.2%). 미리 정한 규칙으로는 128개 중 118개 (86.2%~95.7%). |
| 맞는 문장을 틀렸다고 함 | 322개 중 2개 (0.2%~2.2%) | 322개 중 26개 (5.6%~11.6%) |
| 확인하지 못한 숫자 | 미대조 450개 중 0개, 확인 불가 2개 | 확인할 수 없다고 적은 항목 164개. 평가 문장은 그중에 없음 |
| 문서당 비용 | 0.0075달러, 요청 평균 2.2번 | 0.0013달러, 요청 1번 |

읽을 때 알아 둘 점입니다.

- **미리 정한 대응 규칙은 B 방식을 실제보다 적게 셉니다.** 이 규칙은 지적한 문구에 문장의 숫자가 들어 있을 때만 인정합니다. B 방식은 일곱 번, 맞는 줄에서 숫자 대신 틀린 방향 단어("decreased", "늘었다")를 지목했고, 규칙은 이를 놓친 것으로 셌습니다. 문장이 있는 줄을 지적하면 인정하는 방식으로 세면 B 방식은 128개 중 125개를 잡았습니다. 놓친 3개는 반올림 오류입니다. 맞는 문장을 틀렸다고 한 개수는 두 규칙에서 모두 26개입니다. 이 재집계는 실행 뒤 감사에서 빈틈이 드러나 한 것이어서 두 숫자를 함께 적습니다. 일곱 건의 목록은 [bench/e2/results/heldout-recount-after-audit.md](bench/e2/results/heldout-recount-after-audit.md)에 있습니다.
- **B 방식의 오탐은 대부분 한 가지 관행에서 나왔습니다.** 26개 중 22개가 반올림하지 않고 잘라 쓴 숫자입니다(2.368을 2.36으로). 평가 문제는 이런 숫자를 맞다고 보고, 스크립트도 기본 설정에서 받아들이며, B 방식에도 그렇게 알려 주었습니다. 반올림해 쓴 숫자만 보면 두 방식이 비슷합니다. A는 289개 중 2개, B는 289개 중 4개입니다.
- **계획이 틀리면 맞는 숫자도 틀리게 나올 수 있습니다.** A 방식의 오탐 2개는 한국어 문서 하나에서 나왔습니다. 모델이 배수를 출처의 단위가 아니라 문장에 쓰인 단위에 맞춰 넣었기 때문입니다. 영수증에는 계획이 선언한 배수가 모두 나오므로 읽는 사람이 이를 볼 수 있습니다.
- **A 방식은 두 번 판정을 미뤘습니다.** CSV 출처가 단위를 밝히지 않은 문서 하나에서, 모델의 첫 계획은 배수 100만을 넣어 숫자 2개를 확인됨으로 만들었습니다. 고친 계획에서는 출처가 단위를 밝히지 않는다는 이유로 둘을 거둬들이고 출처 없음으로 표시했습니다.
- **모델 하나로 한 번 돌린 결과입니다.** 다른 모델, 다른 설정, 실제 문서에서는 숫자가 달라질 수 있습니다. 비용도 다릅니다. A 방식은 요청 67번, B 방식은 30번을 썼습니다.
- **연습과 이 실행 사이에 바뀐 것.** B 방식에서는 지적을 문장에 대응시키는 규칙과, 잘라 쓴 숫자도 맞다고 알려 주는 문장이 바뀌었습니다. A 방식에서는 두 번째 연습 뒤에 A 방식의 프롬프트인 스킬 설명서에 두 줄이 늘었습니다. 머리글이 1행에 있지 않은 엑셀 시트와, 여러 칸의 합을 분모로 하는 비중에 관한 내용입니다. 두 방식 모두, 보는 출처에서 엑셀 머리글에 관한 틀린 안내를 뺐고, 답이 잘리거나 실행이 멈추는 경우에 실행기가 견디도록 고쳤습니다. 모두 이유와 함께 평가 계획의 변경 기록에 있습니다. 연습에는 개발용 문서만 썼습니다.

이 실행의 대화, 계획, 스크립트 결과는 모두 [bench/e2/records/heldout](bench/e2/records/heldout)에 있고, 요청별 비용은 [bench/e2/spend.jsonl](bench/e2/spend.jsonl)에 있습니다. 연습을 포함한 E2 전체 비용은 0.36달러입니다.

### E3: 미국 공시(SEC EDGAR)

연결이 돌려준 값을 공시 문서에 인쇄된 숫자와 비교했습니다. 20개 회사마다 가장 최근 10-K와 10-Q를 읽고, 공시 한 건에서 태그가 붙은 숫자를 35개까지 뽑았습니다.

- 2,338번의 판정에서 틀림은 없었습니다.
- 공시를 지정했을 때 1,169개 중 1,167개가 확인됐습니다. 지정하지 않았을 때는 1,145개가 확인됐고, 22개는 공시마다 값이 달라 판정을 미뤘습니다.
- 확인되지 않은 2개는 하루에 지급된 주당 배당금입니다. 공시는 이를 하루짜리 기간으로 태그하는데, SEC API는 날짜 하나로 저장합니다. 그래서 기간이 정확히 맞아야 한다는 규칙으로는 찾지 못했고, 스크립트는 판정을 미뤘습니다. 0.1.1부터는 하루짜리 범위를 날짜 하나와 같게 다룹니다. 0.1.0 배포 뒤에 이 두 수치만 따로 다시 돌려 보니 둘 다 확인됐습니다. 이 확인은 위 결과에 넣지 않았습니다.
- 아무것도 찾지 못해야 하는 위치 지정 800건은 모두 확인 불가로 나왔고, 연락처가 없거나 저장된 파일이 깨졌거나 서버에 닿지 않는 실행 15건은 모두 멈췄습니다.

비교하는 양쪽은 회사가 낸 같은 제출 자료에서 나옵니다. E3가 보는 것은 연결이지, 회사가 공시에 태그를 맞게 붙였는지가 아닙니다. 여섯 번째 기준은 첫 개발용 실행 뒤에 추가했습니다. 일부러 고장 낸 도구 하나가 처음 다섯 기준을 통과했기 때문이고, 경위는 [평가 계획의 변경 기록](docs/eval-plan.md)에 있습니다.

### E4: 한국 공시(DART)

연결이 돌려주는 값을 회사가 낸 XBRL 원본 파일과 견줍니다. 31개 회사의 2025년 사업보고서와 2026년 반기·3분기보고서를 연결과 별도로 읽었습니다. 재무제표 177벌, 금액 44,829개입니다. 11개 회사는 미리 이름을 적어 둔 대형사이고, 20개 회사는 DART 회사 목록에서 종목코드가 있는 나머지 3,999곳 가운데 미리 정한 규칙으로 뽑아, 누구도 고르지 않았습니다. 가능한 186벌 중 9벌은 없습니다. 뽑힌 회사 3곳이 연결재무제표를 내지 않기 때문입니다.

- 틀림으로 판정된 금액은 없었습니다(판정 132,384건). 계정 ID로 물었을 때 44,829개 모두, 계정 이름으로 물었을 때 42,726개 모두, 접수번호를 지정했을 때 44,829개 모두 확인됐습니다.
- 문서에 옆 열의 숫자가 들어간 76,873건은 모두 틀림으로 판정됐습니다. 3개월 자리에 누적 수치, 올해 자리에 작년 수치, 연결 자리에 별도 수치를 넣은 경우입니다.
- 판정을 미뤄야 하는 6,785건은 모두 확인 불가였습니다. 없는 계정, 그 보고서에 없는 열, 보고서가 없는 연도, DART에 없는 재무제표 구분, 자본변동표, 바꿔 넣은 접수번호를 물은 경우입니다. 여러 줄이 같은 이름을 쓰는 줄을 이름으로만 물은 599건도 모두 확인 불가였습니다.
- 10개 회사는 보고서를 정정한 적이 있습니다. 이전 접수번호를 지정한 주장 95건은 모두 확인 불가였고, 같은 금액을 현재 접수번호로 물으면 확인됐습니다.
- 키가 없거나, 저장 파일이 깨졌거나, 서버에 닿지 않거나, DART가 오류 상태를 돌려준 실행 25건은 모두 멈췄습니다. 스크립트가 출력하거나 쓴 어디에도 키는 없었습니다.

알아 둘 점입니다.

- **채점은 세 번 시작했고 셋 다 기록에 있습니다.** 첫 번째는 도는 중에 컴퓨터가 절전 상태로 들어가 10시간 반 동안 멈추면서 끊겼습니다. 윈도우 기록에는 절전 사유가 전원 버튼 또는 덮개로 남아 있습니다. 그때 돌던 계획 4개가 시간 제한을 넘겨 실패로 처리됐고(재무제표 한 벌의 옆 열 문제 628건과 판정 보류 문제 15건), 이 실행은 기준 2개를 미달로 보고합니다. 두 번째는 시작하고 몇 분 뒤, 채점을 띄운 데스크톱 앱이 업데이트되면서 끊겼습니다. 계획 1,583개와 멈춤 문제 25건이 시작조차 못 했고, 이 실행은 기준 6개를 미달로 보고합니다. 최종용 실행 전에 적어 둔 규칙은 도구 밖의 이유로 끊긴 채점은 다시 돌린다는 것입니다. 세 번째는 같은 저장 자료와 같은 코드로 끝까지 돌았고, 위 결과가 그 실행입니다. 실제로 돈 계획만 보면 앞의 두 번도 세 번째와 판정 건수가 같고, 세 번 모두 틀림으로 판정된 금액은 없었습니다.
- **회사를 누가 골랐는가.** 이름을 적어 둔 11곳은 작성자가 골랐고, 작성자는 이전 프로젝트에서 이 11곳의 DART 재무제표를 읽은 적이 있습니다. 뽑은 20곳은 누구도 고르지 않았습니다.
- **비교하는 양쪽은 같은 제출 자료에서 나옵니다.** E4가 보는 것은 연결이지, 회사가 재무제표에 태그를 맞게 붙였는지가 아닙니다.
- **들어 있지 않은 것.** 자본변동표(스크립트가 거부합니다), 표준 계정 ID가 없는 줄(1,344줄), DART가 한 날짜로 태그하는 현금흐름표의 기초·기말 현금 줄(금액 826개)입니다. XBRL 파일에 해당 기간의 값이 없던 금액 1,176개도 뺐습니다.
- **모델은 쓰지 않았습니다.** E4는 스크립트에 맞는 위치를 줍니다. 모델이 DART를 상대로 계획을 쓸 때 열을 얼마나 맞게 고르는지는 E4에서 재지 않았고, E5에서 쟀습니다.
- **도중에 바뀐 것은 모두 최종용 자료를 받기 전의 일입니다.** 평가 문제를 만든 쪽이 개발용 회사에서, DART가 분기·반기 현금흐름표의 비교 열 하나를 서로 다른 두 기간으로 채운다는 것을 찾았습니다. 계약 문서가 틀렸던 것이고, 스크립트는 이제 그 열을 거부합니다. 채점기를 점검하려고 일부러 고장 낸 도구 사본들을 채점했는데 하나가 기준 7개를 통과해서, 여덟 번째 기준을 추가했습니다. 코드를 쓰지 않은 검토자가 연결을 깨 보려고 두 번 시도했습니다. 확인된 문제는 고쳤고, 한 가지 한계는 계약 문서에 적어 두었습니다. 응답의 각 줄에는 연결인지 별도인지 표시가 없다는 점입니다. 단계마다의 기록은 [평가 계획의 변경 기록](docs/eval-plan.md)에 있습니다.

### E5: 모델이 DART를 상대로 계획을 쓸 때

E4는 스크립트에 맞는 위치를 주었습니다. E5는 모델이 그 위치를 직접 찾게 합니다. 문서는 회사 하나의 보고서 하나를 다룬 짧은 한국어 메모이고 문장이 12개입니다. 그중 4개에 오류를 심었습니다. 석 달 수치와 누적 수치를 바꿔 넣거나, 이번 기간과 비교 기간을 바꿔 넣거나, 연결과 별도를 바꿔 넣거나, 금액을 3~30% 바꾸거나, 증감률이나 비율을 틀리게 쓴 것입니다(마지막 종류 18개 중 4개는 크기는 맞고 늘었다·줄었다만 반대로 썼습니다). 정답은 E4처럼 회사의 XBRL 파일에서 나옵니다. 회사는 E4의 최종용 31곳이고 스크립트와 스킬은 0.2.0 그대로입니다.

같은 모델(Claude Haiku 5.5)로 두 방식을 돌렸습니다. 스킬 쪽은 문서와 스캔 결과, 그리고 도구 3개를 받습니다. 둘은 조회 명령을 대신해 회사, 줄, 열을 보여 주지만 금액은 보여 주지 않고, 하나는 계획 양식 문서를 돌려줍니다. 모델이 계획을 쓰면 스크립트가 판정하고, 모델은 계획을 두 번까지 고칠 수 있습니다. 판정 뒤에 모델이 읽는 영수증에는 계획이 읽은 칸의 금액이 나옵니다. 혼자 쪽은 문서와 해당 보고서의 재무제표를 글로 받습니다. 재무상태표, 손익계산서, 현금흐름표의 모든 줄과 계획 양식이 정한 금액 열이 들어 있고 한 번의 요청으로 검토합니다.

| | 스킬과 스크립트 | 모델 혼자 |
|---|---|---|
| 심은 오류를 잡음 | 124개 중 124개(95% 구간 97.0~100%) | 124개 중 120개(92.0~98.7%). 손으로 읽으면 124개, 아래 참고 |
| 맞는 문장을 틀렸다고 함 | 248개 중 0개(0~1.5%) | 248개 중 2개(0.2~2.9%) |
| 문서당 요청 수 | 4~8번, 평균 5.7번 | 1번 |
| 문서당 비용 | 0.021달러 | 0.0019달러 |

- **모델은 칸을 찾았습니다.** 스크립트가 판정한 숫자 371개 중 367개는 문장이 뜻하는 바로 그 칸에서 읽었습니다. 나머지 4개는 같은 연말 잔액을 분기보고서의 비교 열 대신 사업보고서에서 읽었습니다. 날짜와 금액이 같습니다. 맞는 숫자 1개는 미대조로 남았습니다. 모델이 계획 세 개 모두에서 음수 금액 `-88억원`을 연결하지 못했습니다.
- **숫자에 맞춰 계획을 고친 경우는 없었습니다.** 모델은 문서 8개에서 계획을 10번 고쳤습니다. 그중 5개 문서는 첫 계획에서 칸을 `operands` 밖에 적어, 스크립트가 숫자 12개 중 10개를 판정할 수 없다고 돌려보냈습니다. 계획 사이에 바뀐 판정 52개는 모두 확인 불가나 미대조에서 바뀐 것입니다. 이미 틀림이나 확인됨으로 나온 숫자는 하나도 바뀌지 않았습니다.
- **스킬은 비슷한 수를 잡았습니다.** 실행 전에 정한 규칙으로는 스킬 쪽 124개 중 124개, 혼자 쪽 124개 중 120개이고 95% 구간이 겹칩니다. 손으로 읽으면 두 쪽 모두 124개를 다 잡았습니다. 혼자 쪽은 맞는 보고서를 건네받았고 금액을 봤습니다. 스킬 쪽은 회사, 보고서, 줄을 직접 찾아야 했고 문서당 비용이 약 11배였습니다. 여기서 스킬이 더해 주는 것은 숫자마다 남는 영수증입니다.
- **답 하나는 읽지 못했습니다.** 혼자 쪽의 답 하나가 올바른 JSON이 아니었습니다(마침표 하나가 잘못 들어감). 실행 전에 정한 규칙은 이런 답을 아무것도 지목하지 않은 것으로 봅니다. 그러면 124개 중 120개입니다. 손으로 읽으면 그 문서에 심은 4줄만 지목했고, 그러면 124개 중 124개입니다.
- **혼자 쪽이 틀린 곳.** 놓친 4개는 모두 읽지 못한 답 하나에 있고, 미리 이름을 적어 둔 대형사 11곳 중 한 곳의 사업보고서 문서입니다. 맞는 문장을 틀렸다고 한 2개도 대형사 문서이고 모델 자신의 계산 실수였습니다. 규칙으로 뽑은 20곳에서는 두 쪽 모두 심은 오류 80개 중 80개를 잡았고 맞는 문장 160개 중 0개를 틀렸다고 했습니다.
- **출처 없이도 보이는 오류가 있습니다.** 124개 중 39개는 같은 금액이 다른 줄에도 있거나, 그 수치의 입력값이 문서에 적혀 있거나, 그 금액이 문서에 적힌 맞는 증감률·비율의 입력값이고 나머지 입력값도 문서에 있습니다. 이것을 빼면 스킬 쪽 85개 중 85개, 혼자 쪽 85개 중 82개입니다(놓친 3개는 읽지 못한 답에 있습니다).

유의할 점: 메모는 문장 틀로 만들었고 문장마다 연결·별도와 기간을 적었습니다. 실제 메모는 더 어렵습니다. `7~9월` 표기는 쓰지 않았습니다. 0.2.0의 스캔이 앞 숫자를 문서의 숫자로 세기 때문이고, 0.2.1에서 고쳤습니다. 모델 하나, 설정 하나로 한 번 돌린 결과입니다. 통과 기준은 없었습니다. 종류별로 혼자 쪽은 a 21개 중 21개, b 31개 중 30개, c 27개 중 26개, d 27개 중 26개, e 18개 중 17개를 잡았고 스킬 쪽은 모두 잡았습니다. 실행 전에 코드를 쓰지 않은 에이전트가 생성기, 실행기, 채점기를 검토했고 그 지적은 최종용 문서를 만들기 전에 고쳤습니다. E5 전체 비용은 연습 두 번을 포함해 요청 258번, 0.90달러입니다. 대화, 도구 호출, 모든 계획은 [bench/e5/records](bench/e5/records)에 있습니다.

### 재지 않은 것

- 스킬 이름을 말하지 않았을 때 에이전트가 스킬을 불러오는지.
- Claude Code가 아닌 에이전트, 그리고 앱 안에서 치는 `/plugin` 명령(명령줄 방식만 확인했습니다).
- 모델이 EDGAR를 상대로 계획을 쓰는 경우. E2는 파일만 썼고 E5는 DART를 다룹니다.
- 실제 문서. 실제 문서를 대조한 사례를 예로 실을 수는 있지만 성능 추정치는 아닙니다.

### 실행 기록

도구를 채점한 실행은 모두 커밋 번호와 함께 남아 있습니다. E1은 [bench/runs.jsonl](bench/runs.jsonl), E2는 [bench/e2/runs.jsonl](bench/e2/runs.jsonl), E3는 [bench/edgar/runs.jsonl](bench/edgar/runs.jsonl), E4는 [bench/dart/runs.jsonl](bench/dart/runs.jsonl), E5는 [bench/e5/runs.jsonl](bench/e5/runs.jsonl)입니다. E1~E4의 개발용 실행도 같은 파일에 있습니다. E5의 연습 두 번은 채점했지만 기록 파일에 남기지 않았습니다. E1, E2, E3는 코드를 커밋 `a84647c`에서 동결했고, 최종용 실행은 결과와 기록만 다른 그 뒤 커밋에서 했습니다. 0.1.1과 0.2.0은 그 뒤에 코드를 바꿨습니다. E1, E2, E3의 최종용 문제는 다시 돌리지 않았고, 두 버전 모두 개발용 문제로만 다시 돌려 E1과 E3의 기준을 모두 충족했습니다. E4는 코드를 커밋 `2ae4742`에서 동결했고, 최종용 채점 세 번은 `f3a841c`, `nogit`(앱이 업데이트되는 동안 git을 실행하지 못했습니다), `79dafe1`로 기록돼 있습니다. E5의 최종용 실행은 `15b4dc5`에서 했고 채점은 `f74ce9e`로 기록돼 있습니다. 일부러 고장 낸 도구 사본을 채점한 실행은 이 파일들에 없고, 평가 계획의 변경 기록에 적었습니다.

## 로드맵

0.1.0에 들어간 것: 대조 스크립트와 평가 문제, 스킬과 플러그인, 미국 공시 연결, 평가 세 가지. 0.1.1에 들어간 것: EDGAR의 하루짜리 기간. 0.2.0에 들어간 것: 한국 공시(DART) 연결과 그 평가.
